# План разработки приложения «Свояк»

**Документ:** `docs/PLAN.md`
**Архитектура:** Next.js-монолит с собственным Node.js-сервером
**Язык:** TypeScript
**Режим работы:** локальная сеть без обязательного доступа к интернету

---

# 0. Инициализация и настройка проекта

## Цель версии

Создать воспроизводимую основу проекта, на которой можно последовательно реализовывать сервер, интерфейсы, Socket.IO, редактор викторин и игровые сценарии.

После завершения нулевого этапа приложение должно запускаться одной командой в режиме разработки, проходить проверку типов, линтинг и форматирование.

---

## 0.1. Создание Next.js-проекта

Создать приложение с параметрами:

- Next.js;
- App Router;
- TypeScript;
- Tailwind CSS;
- каталог `src/`;
- ESLint;
- без каталога `pages/`.

Рабочая структура:

```text
swoyak/
├── src/
│   ├── app/
│   ├── components/
│   ├── features/
│   ├── server/
│   ├── shared/
│   ├── stores/
│   └── styles/
├── games/
│   └── assets/
├── public/
├── tests/
├── docs/
├── server.ts
├── next.config.ts
├── package.json
└── tsconfig.json
```

Создать пустые `.gitkeep` в каталогах, которые Git иначе не сохранит:

```text
games/.gitkeep
games/assets/.gitkeep
```

---

## 0.2. Установка runtime-зависимостей

Установить библиотеки для основной функциональности:

```text
socket.io
socket.io-client
zustand
zod
slugify
qrcode
archiver
unzipper
file-type
sharp
```

Назначение:

- `socket.io` — WebSocket-сервер и управление комнатами;
- `socket.io-client` — подключение браузеров;
- `zustand` — клиентское состояние редактора и интерфейсов;
- `zod` — проверка конфигов, API и Socket.IO payload;
- `slugify` — создание безопасных имён конфигов и архивов;
- `qrcode` — генерация QR-кода комнаты;
- `archiver` — создание ZIP;
- `unzipper` — чтение и распаковка ZIP;
- `file-type` — проверка реального типа загруженного изображения;
- `sharp` — проверка и нормализация изображений.

Для SHA-256 использовать встроенный модуль Node.js:

```text
node:crypto
```

Для файловой системы использовать:

```text
node:fs/promises
node:path
```

## 0.4. Настройка собственного сервера

Создать `server.ts`, который:

1. запускает Next.js;
2. создаёт Node.js HTTP-сервер;
3. подключает Socket.IO;
4. слушает адрес `0.0.0.0`;
5. использует настраиваемый порт;
6. выводит локальные адреса приложения;
7. корректно завершает сервер по `SIGINT` и `SIGTERM`.

Добавить команды:

```json
{
  "scripts": {
    "dev": "tsx watch server.ts",
    "build": "next build",
    "start": "NODE_ENV=production tsx server.ts",
    "typecheck": "tsc --noEmit",
    "lint": "next lint",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:e2e": "playwright test",
    "check": "npm run typecheck && npm run lint && npm run format:check && npm run test"
  }
}
```

Команды должны быть адаптированы под фактическую версию Next.js и используемый package manager.

# 1. Версия 0.1 — LAN Buzzer Prototype

## Цель версии

Реализовать минимальную сетевую игру без настоящих викторин: ведущий создаёт комнату, игроки подключаются и соревнуются в нажатии кнопки.

---

## 1.1. Контракты Socket.IO

Codex должен предложить и реализовать типизированные контракты для:

- создания комнаты;
- подключения игрока;
- переподключения;
- открытия кнопок;
- нажатия;
- определения победителя;
- закрытия кнопок;
- состояния игрока;
- ошибок.

Разместить контракты в:

```text
src/shared/contracts/
```

Payload каждого входящего события должен проверяться через Zod на сервере.

---

## 1.2. Менеджер комнат

Реализовать серверный `RoomManager`.

Функции:

- создать комнату;
- сгенерировать уникальный короткий код;
- найти комнату;
- добавить игрока;
- удалить игрока;
- пометить игрока отключённым;
- восстановить подключение;
- удалить неактивную комнату;
- получить публичное состояние.

Активные комнаты пока хранятся в памяти.

---

## 1.3. Создание комнаты

Создать страницу ведущего:

```text
/host
```

Функции:

- кнопка «Создать комнату»;
- отображение кода;
- отображение локальной ссылки;
- QR-код;
- список подключённых игроков;
- отображение локального IP и порта.

---

## 1.4. Подключение игрока

Создать страницы:

```text
/join
/join/[roomCode]
```

Функции:

- ввод кода;
- ввод имени;
- проверка комнаты;
- защита от одинаковых имён;
- сохранение токена игрока в `localStorage`;
- переход на игровой экран.

---

## 1.5. Экран игрока

Создать:

```text
/player/[roomCode]
```

На экране находятся только:

- имя;
- количество баллов;
- большая кнопка;
- нижний прогресс-бар.

Требования:

- нет общей прокрутки;
- кнопка находится в центре;
- кнопка всегда видима;
- кнопка получает DOM-фокус;
- работают касание, мышь, `Space` и `Enter`;
- `event.repeat` игнорируется.

Баллы на этой версии можно держать равными нулю.

---

## 1.6. Открытие кнопок

На экране ведущего добавить:

- настройку длительности тестового окна;
- кнопку «Открыть кнопки»;
- кнопку «Закрыть кнопки»;
- имя первого нажавшего;
- кнопку «Сбросить попытку».

Сервер создаёт уникальный:

```text
buzzWindowId
```

Он должен меняться при каждой новой попытке.

---

## 1.7. Нижний прогресс-бар

Реализовать компонент `BottomProgress`.

Требования:

- находится у нижнего края;
- уменьшается от краёв к центру;
- стили анимации находятся в `src/styles/bottom-progress.css`;
- время рассчитывается по серверным временным меткам;
- компонент используется ведущим и игроками;
- завершение анимации клиента не является источником истины.

---

## 1.8. Определение первого игрока

Сервер должен атомарно принять только одно первое допустимое нажатие.

Проверки:

- комната существует;
- игрок находится в комнате;
- окно открыто;
- `buzzWindowId` актуален;
- время не истекло;
- победитель ещё не выбран;
- игрок ещё не отправлял событие в это окно.

После определения победителя:

- кнопка победителя меняет состояние;
- кнопки остальных блокируются;
- ведущий видит имя победителя.

---

## 1.9. Базовая защита от повторных событий

Реализовать:

- leading-edge обработку;
- single-flight lock на клиенте;
- одно событие на `buzzWindowId`;
- игнорирование `event.repeat`;
- серверную защиту от повторного события.

Полный rate limit переносится в версию 0.5.

---

## 1.10. Тесты версии

Unit-тесты:

- генерация уникальных кодов;
- подключение игрока;
- защита от одинаковых имён;
- первое нажатие принимается;
- второе нажатие отклоняется;
- старый `buzzWindowId` отклоняется;
- нажатие после времени отклоняется.

E2E:

1. ведущий создаёт комнату;
2. два игрока подключаются;
3. ведущий открывает кнопки;
4. один игрок определяется победителем;
5. повторный запуск работает.

---

## Критерии готовности версии 0.1

- минимум три телефона подключаются к компьютеру ведущего;
- работают код, ссылка и QR-код;
- кнопка не требует прокрутки;
- первый игрок определяется только сервером;
- все клиенты получают согласованное состояние;
- окно нажатия можно перезапускать;
- `npm run check` проходит.

# 2. Версия 0.2 — Quiz Alpha

## Цель версии

Реализовать создание текстовых викторин до запуска комнаты и полный базовый игровой цикл.

---

## 2.1. Доменная модель викторины

Codex должен предложить:

- TypeScript-типы;
- Zod-схемы;
- версионирование конфига;
- правила идентификаторов;
- правила стоимостей;
- структуру настроек.

Обязательные сущности:

- викторина;
- раунд без пользовательского названия;
- тема;
- вопрос;
- текст вопроса;
- правильный ответ;
- комментарий ведущего;
- стоимость;
- временные настройки.

---

## 2.2. Файловое хранилище

Реализовать серверный `QuizRepository`.

Функции:

- получить список викторин;
- получить викторину;
- создать викторину;
- обновить викторину;
- удалить викторину;
- проверить существование slug;
- атомарно сохранить JSON;
- не допускать записи вне `games/`.

На этой версии изображения ещё не используются.

---

## 2.3. Библиотека викторин

Создать:

```text
/library
```

Функции:

- список сохранённых викторин;
- название;
- количество раундов;
- количество вопросов;
- дата изменения;
- создать;
- открыть;
- продублировать;
- удалить;
- перейти к созданию комнаты.

---

## 2.4. Редактор викторины

Создать:

```text
/editor/new
/editor/[quizId]
```

Функции:

- название викторины;
- автоматический slug;
- ручное редактирование slug;
- настройки временных интервалов;
- добавление раунда;
- удаление раунда;
- изменение порядка раундов;
- добавление темы;
- переименование темы;
- удаление темы;
- изменение порядка тем;
- добавление вопроса;
- стоимость;
- текст;
- правильный ответ;
- необязательный комментарий ведущего;
- удаление вопроса;
- сохранение.

Использовать Zustand для черновика редактора.

---

## 2.5. Защита несохранённых изменений

При выходе из редактора с несохранёнными изменениями показывать подтверждение.

Хранилище должно различать:

- сохранённое состояние;
- текущий черновик;
- состояние `dirty`;
- выполняющееся сохранение;
- ошибки сохранения.

---

## 2.6. Выбор викторины для комнаты

Создание комнаты должно включать выбор ранее сохранённой викторины.

Последовательность:

1. ведущий выбирает викторину;
2. создаёт комнату;
3. сервер создаёт снимок конфига;
4. игроки подключаются;
5. ведущий запускает сессию.

Редактирование исходной викторины не должно менять запущенную сессию.

---

## 2.7. Игровая сетка

Реализовать экран текущего раунда:

- столбцы — темы;
- ячейки — стоимости;
- сыгранные вопросы блокируются;
- названия раундов формируются автоматически;
- ведущий выбирает вопрос;
- публичный экран пока может быть объединён с экраном ведущего.

---

## 2.8. Предварительная задержка

После выбора вопроса:

1. фаза меняется на `question-intro`;
2. показываются тема и стоимость;
3. запускается `questionIntroSeconds`;
4. кнопки игроков отключены;
5. после задержки автоматически показывается вопрос;
6. кнопки автоматически открываются;
7. запускается `buzzSeconds`.

---

## 2.9. Ответ игрока

После первого нажатия:

- фиксируется отвечающий игрок;
- запускается визуальный `answerSeconds`;
- ведущий видит текст вопроса;
- ведущий видит правильный ответ;
- ведущий видит `hostComment`;
- таймер не принимает решение автоматически.

---

## 2.10. Оценка ответа

Добавить действия:

```text
Верно
Неверно
Не успел
```

После выбора оценки баллы не меняются.

Сервер создаёт предложение изменения баллов.

---

## 2.11. Подтверждение баллов

Реализовать отдельную фазу:

```text
score-confirmation
```

Ведущий видит:

- имя игрока;
- результат;
- стоимость вопроса;
- предложенное изменение;
- числовой input;
- «Подтвердить»;
- «Отмена».

Только подтверждение изменяет счёт.

Проверки сервера:

- proposal существует;
- proposal принадлежит текущему вопросу;
- proposal ещё не применён;
- delta является допустимым целым числом;
- повторное подтверждение невозможно.

---

## 2.12. Неправильный ответ

После подтверждения:

- игрок добавляется в `attemptedPlayerIds`;
- его кнопка отключается;
- для остальных автоматически запускается новое окно нажатия;
- создаётся новый `buzzWindowId`;
- вопрос остаётся активным.

Если допустимые игроки закончились:

- показывается правильный ответ;
- запускается время раскрытия;
- затем возвращается сетка.

---

## 2.13. Правильный ответ

После подтверждения:

- вопрос помечается сыгранным;
- правильный ответ раскрывается;
- запускается `answerRevealSeconds`;
- затем приложение возвращается к сетке.

---

## 2.14. Завершение раунда и викторины

Реализовать:

- автоматическое определение завершённого раунда;
- переход к следующему раунду;
- ручное завершение сессии;
- итоговую таблицу;
- сортировку по баллам.

---

## 2.15. Тесты версии

Unit:

- CRUD викторины;
- валидация конфига;
- уникальная стоимость внутри темы;

Архив должен содержать ровно:

- `assets/` существует даже без изображений;
- все пути относительные;
- все используемые изображения присутствуют;
- лишние изображения запрещены или явно исключаются при экспорте.

- `contentDigest`.

Создать отдельный модуль:

```text
src/server/package/integrity.ts
```

Написать тесты на одинаковый digest при одинаковом содержимом.

- отправить ZIP;
- удалить временный файл.

- symlink;

- изображения;

- digest;
- дублирующиеся пути;
